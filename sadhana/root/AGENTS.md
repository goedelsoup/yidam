This repository is a living knowledge artifact. Its git history is the knowledge graph:
files are nodes, commits are knowledge events, links are edges.

## The short version

- **Nodes** are files in [`.yidam/corpus/`](.yidam/corpus/), one concept each, each linking
  to at least one other. Add one when an edge needs a target that does not exist yet, never
  speculatively. An edge between existing nodes is a contribution in its own right.
- **Sources** are files in [`.yidam/catalog/`](.yidam/catalog/). Nodes cite them by link,
  not inline.
- **Claims** carry `[verified]`, `[inference]` or `[open]`. Untagged inference is a defect.
- **Commits** are permanent knowledge events. Every subject begins `<verb>: ` from the closed
  vocabulary in [GRAPH.md](.yidam/.vendor/prelude/GRAPH.md), with no `(scope)`, and says
  what changed and why — a merge too. Epistemic and operational commits never mix.
  `yidam vocabulary --check "<subject>"` asks before the commit exists.
- **Provenance is kept.** Do not delete or rewrite a committed node without a record of why.
- **`.yidam/.vendor/` is read-only.** An edit there is discarded by the next
  `mise run yidam-vendor-update`. Nothing upstream can see this repository, so send a
  prelude defect back in one of the two shapes
  [upstream.md](.yidam/.vendor/prelude/guidelines/upstream.md) gives.

## Reading the corpus

**Do not navigate this corpus with `grep`.** It is a typed graph: `grep` finds a string, and
these find nodes, edges and coverage gaps.

```sh
yidam due                       # what is owed — stale index, expired sources, open questions
yidam query '<class> -<rel>-> <class>'   # a typed path; `<-rel-` walks it backwards
yidam neighbors <class>/<node>.yml       # one node's neighbourhood, both directions
yidam estimate '<query>'                 # what an answer would cost, before paying it
yidam pack '<query>' --budget 4000       # that answer as prose, filled to a budget
```

**An empty `query` says why**: the class is not declared, it holds nothing, none of its
instances carries that value (and here are the values they do), or nothing authors that
relationship. Zero `grep` hits say none of that. A misspelled class or relationship is
**rejected with the near miss named**, never returned empty, and `mise run ci` never sees a
query, so nothing else will tell you.

[Reading the corpus](.yidam/.vendor/prelude/guidelines/reading-the-corpus.md) has the full
surface and the worked examples.

## The gate

```
mise run regen           # refresh REGEN blocks, then commit the result as `regen:`
mise run ci              # the whole gate; the README's gate table lists its steps
```

`mise run ci` is what CI runs, held to it by a test upstream. Run it before committing, and
run it whole: `graph-check` is blind to a stale REGEN block and `regen --check` to a broken
edge.

`yidam lint` gates against `.yidam/lint-baseline.yml`, not against zero: it asks whether
*this change* made the corpus less clean. It fails on an error-severity violation not in the
baseline, and on a baseline entry that no longer occurs, because a baseline that over-lists
silently re-permits what it over-lists. Fix the corpus, then `mise run graph-lint-bless` and
commit the diff.

Three checks report and never gate:

- `unauthored-prose-link` covers material this repository did not author, declared in
  `.yidam/authorship.yml`. Fix the generator or raise it upstream. Never baseline it, and never
  edit an import to satisfy a linter.
- `authorship-region-stale` says a declaration there matches nothing on disk.
- `graph-lint-gate` adds `--commits`, this branch's subjects against the closed vocabulary.
  History cannot be rewritten to fix a verb, so ask before committing.

`mise run graph-lint-explain` prints each check's rationale. Read it before deciding a
check is wrong.

The declaration narrows the loop and may not widen the model, and **it binds nobody**:
divergence from it is a question for a person, not a defect. `yidam kuten check` reports
where this repository's history and its declaration disagree, writes nothing, and exits zero.
Change it by a `decide:` commit carrying a superseding decision record — never by editing the
vendored profile, which is discarded on the next re-vendor.

## Governance

This repository is `governance: collective`. Electors are listed in
[`.yidam/sangha/electors.md`](.yidam/sangha/electors.md); the resolution algorithm is in
[`.yidam/sangha/PROTOCOL.md`](.yidam/sangha/PROTOCOL.md). Commit your working position to
your own `ma/<elector>` branch. Do not synthesize another elector's position into yours
outside a resolution event — Article V limits resolution to synthesis of what electors
actually hold.

Before a resolution, **write your position down** in
[`.yidam/sangha/positions/`](.yidam/sangha/positions/). The branch tip records which nodes
you hold; it does not record why, what you conceded, or which of your own earlier grounds
you are withdrawing — and that is what the resolution turns on.

Then **transport it onto the baseline**, unmodified, so the other electors can answer it:
`transport: <whose position, and what it says>`, naming the `ma/<elector>@<hash>` you read
it from. Carrying a file verbatim introduces nothing its author did not hold, which is why
it is legal outside a resolution event — but editing what you carry is not. A position left
on your own branch is one nobody can answer and no corpus node can cite.

The resolution procedure is a loop: state, transport, read the others, answer, repeat until
a round adds nothing. One round is a complete cycle. After the resolution, take the new
baseline by merge, not rebase: `adopt: the baseline after <evolution>`.
