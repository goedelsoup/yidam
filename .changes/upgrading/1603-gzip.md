### A source pack's request permits gzip

**`catalog-fetch` sends `Accept-Encoding: gzip` to a publisher, and holds a gzip-coded answer decoded (#1603).**

A server that refused an uncompressed request, such as eCFR's versioner, now answers.
A server that already answered uncompressed sends the same bytes, so its records keep their sha256.
A server may gzip its answer unasked, as an S3 object stored with `Content-Encoding: gzip` does.
Such an answer was held compressed and is now held decoded.
Its next fetch records a new sha256, of the content rather than of its coding.
A body that is itself a gzip file is still held as served.
That is a body served as `application/gzip`, or at a `.gz` or `.tgz` path.
Decoding stops once a body passes 200 times the bytes sent, past a 64 MiB floor, and nothing is held.
Vault, bundle and cluster downloads still keep the stored bytes exactly, since reqwest decodes nothing in this build.
